# The overlay cascade hot-reloads the running process; it never respawns it

A station→channel→block overlay cascade resolves to one whole config, deepest declared level wins, no merge. Applying a different resolved config at a block boundary hot-reloads it into the channel's already-running `etv-overlay pipe` process — the daemon writes the resolved config to the location `program_context.rs` already polls, and the process reloads script and layers when it sees the file change — rather than killing and respawning that process. A `width`/`height`/`framerate`/`pixel_format` change is rejected at config-load time instead, since those are baked into the running process's fifo byte layout and cannot be hot-reloaded. A cascade level may also declare `overlay: {extend: {layers: [...]}}` to keep the level above's resolved config and append layers to it, each re-rooted against its own config file's directory — append is the only composition allowed, it may not carry geometry, and it may not reach into or modify a layer it inherited; a plain `overlay:` still replaces the whole config, and `clear` still empties the chain, so an extend beneath a cleared ancestor has nothing to extend and fails at load.
